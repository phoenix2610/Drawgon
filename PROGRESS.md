### Notable fixes along the way (kept here so the reasoning isn't lost)

- `database/` and `database/seed/` needed their own `package.json` (`"type": "commonjs"`) — they sit under the frontend's `"type": "module"` package.json, so Node/TS would otherwise try to load migration files as ESM.
- `database/node_modules` is a symlink to `backend/node_modules` — migration/seed files live outside `backend/`, so this is what lets both Node's `require()` and TypeScript's type-checker find `typeorm` via the normal node_modules walk-up (replaced an earlier `NODE_PATH` workaround, which only helped runtime resolution, not type-checking).
- The app's runtime `TypeOrmModule.forRoot()` config omits the `migrations` array — TypeORM eagerly loads every migration file glob on `initialize()` regardless of `migrationsRun`, which would otherwise make the *running app* try to require `.ts` migration files it can't compile.
- Pinned backend `typescript` to `6.0.2` (matching the frontend's own `setup.md` pin). `@nestjs/cli@11.0.24`'s incremental-build integration silently emits zero output files under `typescript@5.9.3` (no error, exit 0, empty `dist/`) — a real upstream incompatibility, not a config mistake on our end. 6.0.2 also introduced two of its own stricter behaviors that needed small fixes: `baseUrl` is deprecated (removed it, `paths` now resolve relative to each tsconfig instead), and ts-jest needs an explicit `rootDir` when compiling `test/` in isolation.
- Class fields on the `Board` entity and the env-validation DTO need `!` definite-assignment assertions — idiomatic for TypeORM entities/class-validator DTOs whose properties are populated by decorators/the ORM, not a constructor.

Zero console errors at every step.

## Phase 1 — Auth — DONE

Built after Phase 2, once there were real boards worth protecting — the user chose this order specifically so community features (next) would have actual multiple accounts to demo with, rather than one placeholder user.

- Server: `better-auth@1.7.1` via `betterAuth({...})` in `backend/src/common/auth/auth.instance.ts` (Kysely `PostgresDialect` over a `pg` `Pool`, `emailAndPassword: { enabled: true }`), mounted through `@thallesp/nestjs-better-auth`'s `AuthModule.forRoot({ auth, isGlobal: true })` in `AppModule`. This gives a **deny-by-default global guard** for free — every route needs `@AllowAnonymous()` (used on the health check) or a valid session (everything else) — plus `/api/auth/*` (signup/login/logout/session) and `@Session()`/`UserSession` for reading the current user in controllers.
- `BoardsController` no longer takes a user id from anywhere client-controlled — `@Session() session` and `session.user.id` come from the verified cookie, so `GET/POST /boards` etc. are automatically scoped to the real signed-in user.
- Client: `better-auth/react`'s `createAuthClient` (`src/lib/auth-client.ts`) — `useSession()` for reactive auth state (no separate zustand store; better-auth's client already tracks this, a second source of truth would just be a sync bug waiting to happen), plus `signIn.email` / `signUp.email` / `signOut`. `LoginPage`/`SignupPage` are plain forms; `ProtectedRoute` redirects to `/login` when there's no session and gates `/` and `/boards/:id`.
- DB schema: `better-auth`'s own `user`/`session`/`account`/`verification` tables are hand-written into `database/migrations/*-BetterAuthSchema.ts` from the **real** schema better-auth computes for our config (`getSchema({ emailAndPassword: { enabled: true } })`, imported directly from the installed package) rather than via `@better-auth/cli generate` — that CLI package is currently marked deprecated by the npm registry itself with the wording "Package no longer supported... contact npm Support," which reads as a registry-side flag rather than an ordinary author deprecation notice, so it was avoided rather than run against the project. Same migration widens `boards.owner_id` from `uuid` to `text` (better-auth ids are opaque strings) and adds a real FK to `user.id`.
- Verified thoroughly with Playwright: protected-route redirect when logged out, full signup flow, session persists (real user email shown on dashboard), and — the actual point of doing auth before community — **two independent accounts** (Dave, Erin) each with their own boards: Erin's dashboard correctly shows zero boards, and directly visiting Dave's board URL as Erin gets a clean "Board not found" (backend correctly scopes `findOneOwnedBy` by owner, doesn't leak existence of other users' boards) rather than either an error page or, worse, Dave's actual content. Dave's own board still persists his drawing across a reload. Zero console errors throughout.
- **Known gap, deliberately not chased further**: `backend/test/app.e2e-spec.ts` (the in-process Nest bootstrap test) had to be deleted. `@thallesp/nestjs-better-auth` and `better-auth`/`@better-auth/core` ship **ESM-only** (`import.meta.url`, no CJS build at all) — Node's own runtime handles `require()`-ing them fine via its native ESM interop (confirmed: the real app boots and runs perfectly), but Jest's own sandboxed module loader can't. Chased two fixes: (1) `transformIgnorePatterns` + ts-jest passthrough — dead end, `import.meta.url` has no CommonJS translation, full stop; (2) full Jest ESM mode (`extensionsToTreatAsEsm`, `ts-jest/presets/default-esm`, `--experimental-vm-modules`) — got further, but then our *own* `data-source.ts` broke (`__dirname` doesn't exist in real ESM), which would cascade into migrating the whole backend off CommonJS just to satisfy the test runner. Not worth it for what it'd buy: the actual app is already verified more convincingly via curl + Playwright against a real running server than an in-process Jest bootstrap would prove anyway. Added a real unit test instead (`boards.service.spec.ts`, 5 cases, mocked repository, specifically covering the owner-scoping logic) so `npm run test` isn't just "no tests found" — that file doesn't touch the auth package at all, so it's unaffected.

**Post-Phase-1 fix**: the user spotted a real dark-mode contrast bug on the login/signup screens — inputs got a dark background (`dark:bg-neutral-800`) with no matching light text color, so typed text was dark-on-dark and unreadable. Fixed by giving inputs explicit `text-neutral-900 dark:text-neutral-100`, and gave the page/form containers explicit backgrounds (`bg-neutral-50`/`bg-white` and dark equivalents) instead of relying on unstyled defaults, so the whole page reads as one consistent theme rather than mismatched panels. Verified in both `colorScheme: 'dark'` and `'light'` via Playwright.

## Phase 5 — Community module — DONE

Built next (ahead of Phase 3/4) per the same reasoning as Phase 1 vs. Phase 2 — this is the other half of "real users, real content," and there were now real accounts to demo cross-user interaction with.

- New entities: `Vote` (unique per board+user, `value` +1/-1), `Comment` (flat, with an unused-for-now `parentCommentId` for future threading), `Bookmark` (unique per board+user) — `database/migrations/*-CommunityTables.ts`. Also added a **read-only** `User` entity mapped onto better-auth's own `user` table so the other entities can join for names — declared with the *exact* real column types (`timestamptz`, `unique: true` on email) after `migration:generate` first produced a migration that would've silently altered/dropped columns better-auth actually needs (wrong timestamp type, dropped the email unique constraint) because my first draft of the entity didn't match reality closely enough. Caught by reading the generated SQL before running it, not by luck.
- Also caught in that same generated-migration review: `Board` had no TypeORM relation object pointing at `User` (just a plain `owner_id` column), so the auto-differ didn't recognize the hand-written `FK_boards_owner` constraint from the Phase-1 migration as "belonging" to the schema and generated a migration that dropped it in `up()` and only restored it in `down()` — i.e. applying it would have silently removed a foreign key. Fixed by adding a proper `@ManyToOne(() => User)` relation with `foreignKeyConstraintName: 'FK_boards_owner'` so it lines up with the existing constraint instead of fighting it. General note for later: always read a generated migration before running it, especially once hand-written and auto-generated migrations start touching the same tables.
- `backend/src/modules/community/`: `CommunityController` (`GET /community/boards` feed, `GET /community/boards/:id` detail incl. snapshot, `POST /community/boards/:id/duplicate`), `VotesController` (`PUT`/`DELETE .../vote`, Reddit-style toggle-off-on-repeat-click), `CommentsController`, `BookmarksController`. Feed/detail enrichment (score, my vote, comment count, bookmarked) is batched (one grouped-sum query for scores, one count query for comments, one `IN`-query for bookmarks) rather than N+1 per board.
- `backend/src/modules/boards/`: added `PATCH /boards/:id/visibility` (the "publish" action) — owner-only, toggles `private`/`public`.
- Frontend: `src/features/community/{VoteButtons,BoardCard,CommentThread}.tsx`, `src/pages/{CommunityFeedPage,CommunityBoardPage}.tsx`. `BoardCanvas` gained a `readOnly` prop (`editor.updateInstanceState({ isReadonly: true })` on mount, no autosave listener) for viewing someone else's board.
- **Real gap caught mid-build, not left as a stub**: my first draft of `CommunityBoardPage` tried to source the canvas snapshot from the owner-scoped `GET /boards/:id` (which 404s for anyone but the owner) and would have shown "preview not available" for every board a viewer didn't own — i.e. the actual drawing would never be visible in the community view, which defeats the point. Fixed by having `GET /community/boards/:id` return the snapshot directly (split into a `FeedItemDetail` type so the *list* endpoint still doesn't ship every board's full snapshot).
- **Real layout bug caught by the user, reproduced and fixed**: `BoardPage`'s publish-toggle control was absolutely-positioned over the canvas in the top-left corner, which collided with tldraw's own contextual "quick actions" toolbar (appears near a selected shape) — the tldraw toolbar's higher stacking order intercepted clicks, making the publish button unclickable whenever a shape near that corner was selected. Fixed by switching to a proper header-bar layout (flex column, header + `flex-1` canvas) instead of floating controls over the canvas — same pattern `CommunityBoardPage` already used correctly. Also fixed `BoardCanvas`'s internal wrapper, which hardcoded `h-screen w-screen` (correct only when it fills the whole page, wrong once nested under a header) to `h-full w-full`.
- Verified end-to-end with Playwright across two real accounts: Holly draws + publishes a board; Ian (different account) sees it in the feed, opens it and sees Holly's *actual drawing* rendered read-only (no drawing tools available), upvotes it, comments, and duplicates it; the duplicate shows up in Ian's own dashboard as a private, fully-editable copy. Also re-verified with curl: vote toggling (click same direction twice → removes it), vote switching, unauthenticated feed access → 401, and a private board correctly 404s through the community detail endpoint even for other authenticated users.
